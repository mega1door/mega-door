# إعداد الأدمن الثاني — مسودة للمراجعة فقط

لم تُنفّذ هذه الملفات على Supabase. وجودها في `proposals` لا يفعّل Migration أو Workflow.

## ما أُعيد استخدامه

Supabase Auth والعميل الحالي، وصفحة إعادة تعيين كلمة المرور الحالية. لا توجد كلمات مرور محفوظة في الكود، ولا مفتاح service role، ولا نظام هوية موازٍ.

## التغيير المقترح

- جدول جديد `mega_private.admin_memberships` يربط UUID الحساب بدور `owner` أو `admin`. الوصول المباشر للجدول والمخطط مسحوب من المتصفح.
- يُسجَّل UUID المالك الحالي كمالك دون تغيير صفه في `auth.users` أو كلمة مروره أو صلاحيات مشروع Supabase. يتوقف السكربت إذا لم تتطابق هويته وبريده المؤكد مع الحساب الموجود بالكود السابق.
- `mega_admin_role()` يقرأ صلاحية صاحب JWT الحالي من الجدول ويتحقق من تأكيد بريده. لا يثق بـ`user_metadata` أو بمعرّف يرسله المستدعي.
- `mega_admin_accounts()` يعرض البريد وحالة التأكيد والدور للمالك فقط.
- `mega_approve_admin(uuid)` و`mega_revoke_admin(uuid)` للمالك فقط. لا يمكن اعتماد بريد غير مؤكد أو تعديل دور المالك. الأدمن الثاني لا يستطيع منح الصلاحيات.
- RLS يحمي الكتابة على models وcategories وspec_templates وsite_settings. تبقى قراءات الكتالوج العامة متاحة كما يحتاجها الموقع والمولّد.
- سياسات كتابة Restrictive تمنع السياسات القديمة Permissive من تجاوز شرط الاعتماد. تُسحب امتيازات الجداول التي لا يغطيها RLS، ومنها TRUNCATE.
- حماية كتابة bucket `site-images` تشمل الإضافة والتعديل والحذف. سياسات الصفوف لبقية buckets تبقى كما هي؛ تُسحب امتيازات TRUNCATE/REFERENCES/TRIGGER غير القابلة للتقييد حسب bucket من storage.objects.
- لا توجد أي إضافة إلى فريق Supabase أو أدوار إدارة المشروع. الصلاحية المقترحة خاصة بوظائف الموقع فقط.

## خطوات المالك بعد الموافقة — بالترتيب

1. تشغيل **00_inspect_admin_access.sql** للقراءة فقط في SQL Editor، ثم مراجعة السياسات والمنح وملكية الجداول وواجهات SECURITY DEFINER وViews. هذه المعلومات غير متاحة للمفتاح العام، وقد تتطلب تكييف المسودة. احتفظي بنسخة السياسات والمنح الحالية قبل التغيير.
2. بعد مراجعة النتائج والموافقة الصريحة، اختبار **01_admin_access.sql** في بيئة Supabase معزولة أولاً. ثم تطبيقه على الإنتاج بإذن منفصل. السكربت داخل معاملة؛ إذا فشل فحص هوية المالك أو السياسات أو Storage، لا تتجاوزي الشرط ولا تكملي التطبيق.
3. التحقق في Authentication من السماح بالتسجيل وتأكيد البريد. الفحص العام الحالي أعاد `disable_signup=false` و`mailer_autoconfirm=false`؛ لم نغيّر هذين الإعدادين. التحقق من Site URL ومسارات Redirect المسموحة:
   - `https://mega1door.github.io/mega-door/`
   - `https://mega1door.github.io/mega-door/admin/`
   - `https://mega1door.github.io/mega-door/reset-password/`
4. التأكد أن المالك يستطيع الدخول وأن الكتابة بحساب غير معتمد ممنوعة قبل نشر واجهة التسجيل. نشر الملفات المحلية جميعها يحتاج موافقتك أيضاً؛ لا توجد أتمتة جديدة أو نشر ضمن هذه المهمة.
5. بعد تفعيل الحماية والواجهة، تفتح آلاء صفحة `/admin/` ثم «إنشاء حساب»، وتستخدم بريدها وكلمة مرورها وتؤكد رسالة التفعيل بنفسها.
6. تدخلين بحسابك الحالي إلى «الحسابات»، تتحققين من بريدها المؤكد ثم تختارين «اعتماد كأدمن». لا تحتاجين كلمة مرورها ولا إضافتها إلى Team/Project Members في Supabase.
7. تعيد آلاء التحقق أو تسجّل الدخول، فتستطيع إدارة الموقع. يبقى تسجيل الخروج واسترجاع كلمة المرور مرتبطين بحساب كل شخص.

**ترتيب التفعيل مهم:** الحماية أولاً، ثم الواجهة، ثم التسجيل والاعتماد. الواجهة الجديدة تتوقف عن إنشاء الحسابات إذا لم تكن دالة الصلاحيات متاحة، ولا تستعمل استثناء UID/بريد قديم لتجاوز الفحص.

## الأدلة والحدود

- الاختبارات تشغّل SQL نفسه في PostgreSQL عبر PGlite بالذاكرة، مع مخططات Auth/Storage معزولة وأدوار anon/authenticated حقيقية. اختُبرت عمليات كتابة مباشرة وتزوير role في metadata والسياسات القديمة المتساهلة، ورفض الموافقة الذاتية، وتفعيل وإلغاء الأدمن الثاني، وحماية المالك.
- فُحصت واجهات التسجيل والاستعادة والموافقة بمعالجات فعلية وعميل Supabase بديل، دون إنشاء حساب حقيقي أو إرسال بريد.
- سياسة الإنتاج الفعلية، وملكية جداول Supabase المستضاف، وعمل PostgREST/Auth/SMTP مع هذه المسودة لم تُختبر فعلياً؛ تحتاج مرحلة المراجعة أعلاه. PostgreSQL المعزول لا يحل محل اختبار Supabase المستضاف بعد الموافقة.
- قبل التطبيق يلزم تدقيق أي View أو SECURITY DEFINER قد يتيح مسار كتابة موازياً. لا تدّعي المسودة حماية مسارات إنتاج لم نتمكن من فحصها.
- التراجع عن تغيير مطبّق يتطلب نسخة السياسات والمنح السابقة ومراجعة متوافقة مع نسخة الواجهة؛ لا يُحذف جدول الأدوار عشوائياً ولا تُعطّل RLS لاسترجاع الدخول.

## تشغيل الاختبارات

`npm test` يشمل اختبارات الواجهة والإصلاحات السابقة وRLS، و`npm run test:rls` يشغّل PostgreSQL المعزول وحده. PGlite مضاف كتَبعية تطوير فقط ولا يدخل حزمة الموقع.

في نسخة العمل الحالية `node_modules` مشترك مع نسخة Desktop، لذلك ثُبّت محرّك الاختبار خارج المشروع واستُخدم `MEGA_PGLITE_MODULE` للإشارة إليه؛ لم نعدّل ذلك المجلد المشترك. في checkout مستقل بعد تثبيت package-lock تعمل التبعية باسمها العادي دون هذا المتغير.
